## はじめに

MCP サーバが公開しているツールは `bajutsu_doctor` と `bajutsu_run` の 2 つだけです
（`bajutsu/mcp/tools.py:55`、`:83`）。コマンドは全部で 20 個あります。しかも両方とも、整形済みの
文字列を返します。つまり Model Context Protocol（MCP）で接続したエージェントは、費用のかかる
実機実行を開始することと画面を採点することはできますが、下書きを検証することも、文法を読むことも、
自分が書いたものを採点することもできません。この項目は、Claude を使わないコマンド群を、すでに
それを列挙している分類表を通じて公開し、コマンド側がすでに算出している構造をそのまま返します。

## 動機

エージェントがシナリオを書くときにすることは 5 つです。文法を読み、下書きし、下書きを検証し、
選んだセレクタを採点し、実行後に失敗を読むことです。MCP 越しにできるのは、4 つ目を
実機実行の開始という形で行うことだけで、残りはできません。そこでエージェントはシェルに落ちます。
下書きをファイルに書き、`bajutsu lint <path>` を実行し、標準出力から `ok` という語を読み取ります。
そのどの手順も、MCP 連携が取り除くはずだったものです。

このシェル頼みは、格好が悪いだけではありません。ライブラリがすでに提供しているものより弱いのです。
`lint_text(text)`（`bajutsu/cli/commands/lint.py:28`）はシナリオを**テキストから**検証します。
エージェントはまだディスクに書いていない下書きを渡してエラーを受け取れる — 考えうる限り最も短い
オーサリングのループです。シェルを経由すると、正しいと分かる前にファイルを存在させることを
強いられます。順序が逆です。

返り値が問題の後半です。`bajutsu_run` は標準エラー出力を付け足した `"PASS  <manifest>"` を返し
（`:130-133`）、`bajutsu_doctor` は `render(s)`（`:80`）— 人間向けに整形した採点結果 — を返します。
エージェントは、データクラスがすでに知っていたことを散文から読み取る羽目になります。`audit`、
`coverage`、`impact`、`stats`、`flakiness`、`triage` の 6 コマンドは `--json` フラグの裏ですでに
JSON を出しています。つまりこれらについては構造が存在していて、MCP の層がそれを捨てています。

*どの*コマンドをここに出すかを決める規則は、すでに用意されていて、しかもすでに効いています。
[BE-0101](../BE-0101-ai-free-zero-config/BE-0101-ai-free-zero-config-ja.md) の `CAPABILITIES` 表
（`bajutsu/common/capability/capabilities.py:41`）は、すべてのコマンドをちょうど一度ずつ
「Claude を使う／使わない」に分類し、`test_classification_matches_the_registered_command_set_exactly`
（`tests/test_capabilities.py:24`）は新しいコマンドが未分類のまま残ると失敗します。Claude を
使わない側の集合こそ、エージェントが 2 つ目のモデルを経路に載せずに呼べるコマンドの集合です。

これが入れば、シェルを持たないエージェントのセッションから読者自身が確かめられます。エージェントは
保存していない下書きを検証し、JSON Schema を読み、自分のセレクタを採点し、マニフェストを読みます。
今日はどれも端末を必要とする 4 つの手順です。MCP 越しの `bajutsu audit` は、`--json` が印字するのと
同じ finding のオブジェクトを返し、それについての段落を返しません。

## 詳細設計

### 公開する対象の表と、なぜ規則ではなく表なのか

「Claude を使わないコマンドをすべて公開する」はほぼ正しく、3 か所で誤りです。`serve`、`worker`、
`mcp` は Claude を使いませんが、長時間動き続けるサーバーです。返ってこないツール呼び出しは、
ツールではありません。そこで選択は `bajutsu/mcp/` 内の明示的な表とし、コマンドごとに 1 行、
どのツールになるか、あるいはならない理由のどちらかを持たせます。

- **公開する（端末不要）** — `lint`、`schema`、`audit`、`coverage`、`impact`、`stats`、
  `flakiness`、`trace`、`report`、`export`、`codegen`。これがオーサリングのループです。
- **公開する（証跡の形）** — `approve`。実行で撮影したスクリーンショットを visual のベースラインへ
  昇格させるもので、読むのは端末ではなく実行ディレクトリです。
- **公開する（端末を使う）** — すでにある `run` と `doctor`。
- **公開せず、理由を記録する** — `serve`、`worker`、`mcp`（長時間動くサーバー）。`record` と
  `crawl`（Claude を使う。公開すると、呼ぶ側のエージェントが決定的だと信じているツール呼び出しの
  裏にモデルが入ってしまいます）。`triage` は Claude を使わない既定の経路だけを公開し、`--ai` は
  使えないようにします。`CAPABILITIES` が分類を反転させるフラグを記録しているのと同じ扱いです。

この表が `CAPABILITIES` をちょうど覆っていることを、既存の網羅テストと同じ形のテストで確かめます。
新しいコマンドが増えたとき、2 か所で 2 つの判断が強制され、どちらも記録に残ります。Claude を
使わないか、そして MCP のツールにするか、です。

### 構造化された返り値

公開する各ツールは、そのコマンドがすでに算出している構造を、MCP の境界で一度だけ直列化して
返します。

- `--json` を持つ 6 コマンドは、そのフラグが直列化しているのと同じオブジェクトを返します。MCP の
  ツールは CLI ではなく解析関数を直接呼ぶので、フラグ側の描画結果を読み直すことはありません。
- `lint` は `{ok, errors, provenanceCoverage}` を返します。`lint_text` がすでに返しているリストに、
  CLI が別途印字している BE-0044 の助言を足したものです。
- `doctor` は `render()` のテキストではなく `score()` のデータクラスを返します。整形済みの形は
  フィールドとして残すので、人間に見慣れた採点結果を見せたいエージェントはそれもできます。
- `run` は判定を保ちつつ、分解して読むための 1 行ではなく `{verdict, manifest, runId, stderr}` と
  して返します。`_parse_verdict`（`:28`）が存在するのは、MCP の層が `run` 自身の標準出力を読み
  直しているからです。ランナーをインプロセスで呼ぶツールならこれは要りません。ただしそれはこの
  項目が強制したい範囲を超える変更なので、`run` の内部はそのままにし、返り値の形だけを構造化し、
  なぜ読み直しが残っているのかを docstring に書きます。

### パスだけでなくテキストも受け取る

`bajutsu_lint` は `scenario_text` か `scenario_path` の、ちょうどどちらか一方を受け取ります。
`load_scenario_file(text)` も `lint_text(text)` もすでにテキストを受け取るので、テキストの経路に
かかるのは引数 1 つであって、仕組みではありません。下書きを確かめられるエージェントと、まず
ファイルシステムに書き込まなければならないエージェントとの差がここにあります。

`bajutsu_codegen` も同じ形でテキストを受け取ります。`bajutsu_audit` の静的モードも同様です。
`--repeat` と `--history` の 2 モードはターゲットと実行ディレクトリを必要とするので、パスの形の
ままにします。

### パスの封じ込めは、作り直さず再利用する

エージェントが渡すパス引数は、リソースの URI と同じ意味で信頼できません。リソースのハンドラは
すでに読み取りを実行ルートの内側に封じ込めていますし（`bajutsu/mcp/resources.py:12-48`）、
[BE-0174](../BE-0174-scenario-ref-path-containment/BE-0174-scenario-ref-path-containment-ja.md) は
シナリオの参照について封じ込めを確立しました。新しいツールは 3 つ目の規則を生やさず、この 2 つを
再利用します。シナリオのパスは BE-0174 が `ref` を封じ込めるのと同じやり方で、実行ディレクトリの
パスは `_run_base` が `run_id` を封じ込めるのと同じやり方で扱います。

### この項目が動かさない境界

ここに並ぶツールはすべて Tier-1 です。エージェントは書き、調べるだけで、決定的なゲートには
触れません。`run` の判定は今までどおり機械検証可能なアサーションから出ます。読み取り専用の解析を
エージェントに多く見せることは、判定の経路にモデルを載せることではありません。そして `record` と
`crawl` を除外することが、呼ぶ側が決定的だと受け取るツール呼び出しの裏に *2 つ目の* モデルが
現れるのを防ぎます。

### オーサリングスキルとの関係

[BE-0330](../BE-0330-scenario-authoring-skill/BE-0330-scenario-authoring-skill-ja.md) は、ソース
コードからシナリオを起草し自己検証まで行う Claude Code スキルを提案しています。両者は補い合う
関係にあり、この順で作るべきです。BE-0330 は*エージェントが何をすべきか*を述べ、この項目は
*そのために行う呼び出し*を用意します。検証のためにシェルへ落ちなければならないスキルは、シェルと
チェックアウトがある場所でしか動かないスキルです。BE-0330 が先に入る場合はシェル経由の経路で書き、
後から移すのがよく、2 つの項目がそれぞれ独自の検証経路を持つべきではありません。

### 作業分解（MECE）

1. **公開対象の表**と、`CAPABILITIES` に対する網羅テストを作ります。
2. **構造化された返り値の型** — ツールごとに 1 つのモデルを定め、境界で直列化します。
3. **端末不要のオーサリングツール** — `lint`、`schema`、`audit`、`codegen`。テキストとパスの
   どちらでも受け取れるようにします。
4. **証跡のツール** — `coverage`、`impact`、`stats`、`flakiness`、`trace`、`report`、`export`、
   `approve`。リソースがすでに根を張っている実行ルートを読みます。
5. **端末を使うツール** — 既存の `run` と `doctor` の返り値を作り直します。
6. **パスの封じ込め** — 新しいパス引数すべてについて、リソースと BE-0174 の規則を再利用します。
7. **ワイヤプロトコルのカバレッジ** —
   [BE-0301](../BE-0301-mcp-real-wire-protocol-test/BE-0301-mcp-real-wire-protocol-test-ja.md) の
   round-trip テストを新しいツールへ広げ、Python の関数を呼ぶのではなく実際のトランスポート越しに
   スキーマを動かします。
8. **ドキュメント** — MCP リファレンスのツール表と日本語版を書き、意図的に載せていないコマンドに
   ついても注記します。

## 検討した代替案

- **コマンドラインを受け取る `bajutsu_cli` ツールを 1 つ用意する。** 却下します。名前を変えた
  シェルをエージェントに渡すのと同じで、スキーマも封じ込めもなく、`record`、`crawl`、
  `triage --ai` を締め出す手立てもありません。BE-0101 が効くようにした分類が、この境界では
  強制できなくなります。唯一の実利である「新しいコマンドに MCP 側の作業が要らない」という性質は、
  新しいコマンドが未分類のまま現れられるという性質と同じものです。
- **ツールではなく MCP リソースとしてすべてを公開する。** 却下します。リソースは URI で指して
  読むものですが、ここでの呼び出しは引数（ターゲット、シナリオのテキスト、繰り返し回数）を取り、
  承認を求める価値のある作用を持ちます。読み取り専用の証跡は BE-0018 がすでにリソース側へ置いて
  いて、そこが正しい置き場所です。この項目はそのもう半分です。
- **文字列の返り値のまま、書式をドキュメント化する。** 却下します。ドキュメント化された文字列の
  書式は、スキーマの強制力を持たないパーサの契約です。しかもこのリポジトリはその代償をすでに
  払っています。`_parse_verdict` は `run` 自身が生んだ書式を読み直すために存在し、その docstring は
  どの行を信じるべきかを長々と説明しています。同じ書式を増やすことは、同じ代償を繰り返し払う
  ことです。
- **Typer のアプリを内省してツールを生成する。** 本当に魅力的です。登録は 1 か所で済み、保守する
  表もありません。それでも却下します。登録されているものが何であれ公開してしまい、サーバー群も
  Claude を使うコマンドも含まれます。またツールのスキーマを CLI のオプションから導くことになり、
  それはエージェントが必要とするものではなく端末の作法（`--json`、`--udid "booted"`）を
  符号化したものです。明示的な表は判断が記録される場所で、内省は判断が失われる場所です。

構築の途中で決めるべき論点です。

- 構造化された返り値が既存のエージェント設定にとって破壊的変更になるか、最初のリリースでは両方の
  形を返すべきか。サーバーには今日まだ公開されたバージョンがなく、それは今きれいに変えるべきだと
  いう論拠になります。
- MCP 越しの `run` が進捗をストリームすべきかどうか。プロトコルはそれを支えていますが、今のツールは
  最大 10 分ブロックします（`bajutsu/mcp/tools.py:121`）。エージェントにはハングとして見えます。
- そもそも `codegen` をここに含めるべきかどうか。出力はエージェント自身でも書けるファイルだから
  です。含める側の論拠は、どのフィールドを各ターゲットが拒否するかを知っているのはエミッタであり、
  エージェントがそこを当て推量すると、コンパイルの通らないコードが出てくるということです。
