## はじめに

シナリオを書く作業は反復です。YAML を直し、実行し、失敗を読み、また直します。その 1 周ごとに
新しい `bajutsu run` のプロセスが立ち上がり、新しいプロセスはデバイスプールを起こし、ランナーを
コールド起動し、そしてどちらも畳みます。この項目は `run --watch` を追加します。対象のファイルが
変わったら同じシナリオを再実行し、その間プールを生かしておくものです。変えるのは実行が**いつ**
始まるかであって、実行が**何をするか**ではありません。

## 動機

[BE-0291](../BE-0291-xcuitest-runner-reuse-across-scenarios/BE-0291-xcuitest-runner-reuse-across-scenarios-ja.md)
は、ランナーのコールド起動が iOS の実行における最大の固定費であること — 負荷のかかった継続的
インテグレーションのホストではコールド起動が 10 秒を超えることが日常茶飯事で、ドライバは
それに 120 秒まで許していること — を示し、デバイスごとの環境をプールにキャッシュすることで
実行の*内側*からそれを取り除きました（`bajutsu/common/runner/pool.py:263`）。この償却は本物で、
そして償却が効くのはプールの寿命の内側だけです。`device_pool` は `(lease, shutdown)` の対を返し
（`:142`）、`shutdown` は実行の終わりに走ります。

執筆の反復は 1 回の実行ではなく、何度もの実行です。ですから反復は、BE-0291 が実行の内側から
取り除いたその費用を、毎周まるごと払います。しかもセレクタを 1 つ変えただけの、考えうる限り
小さな編集に対しても払います。償却は、人間の反復が始まるちょうどその場所で止まっています。

もう 1 つの費用はもっと小さく、そしてもっと苛立たしいものです。編集の途中で保存されたシナリオは
不正な YAML です。実行は読み込みエラーで終わり、著者はコマンドを打ち直します。この往復のどこにも、
ツールがまだ知らなかった情報はありません。

これが入れば、showcase のスイートで読者自身が確かめられます。`run --watch` を開始し、シナリオを
編集すると、2 周目はランナーのコールド起動なしに始まります。同じデバイスと同じランナーが 1 周目を
担ったからです。各周が印字する判定行は `bajutsu run` が印字するものと同じで、各周は自分の実行
ディレクトリを書くので、`trace` も `report` もどの周に対しても動きます。

## 詳細設計

### 1 周は、コールドな 1 回の実行そのもの

これはこの設計で唯一譲れない点です。watch モードが周をまたいで持ち越すのは**インフラ** — 起動済みの
デバイス、常駐しているランナー、ブラウザのコンテキスト — だけで、**アプリケーションの状態**は
一切持ち越しません。毎周は今日の `run` と同じように lease を取り、つまりアプリを再起動し、最初の
ステップから `before`／`after` のフック
（[BE-0392](../BE-0392-scenario-before-after-hooks/BE-0392-scenario-before-after-hooks-ja.md)）まで
シナリオを実行します。再開はありませんし、「失敗したステップからやり直す」もありませんし、前の周が
残した画面を使い回すこともありません。

理由は第二原則です。前の周がアプリを正しい画面に残していたおかげで通るシナリオは、CI のどの実行も
再現しない理由で通るシナリオであり、著者は決定的なゲートが決して見ない状態を相手にデバッグする
ことになります。魅力的に見える機能 — 壊れたところから再開する — こそ、この項目が拒む機能であり、
後から気づかれるのに任せず本文で拒みます。

### プールを 1 段上のスコープへ移す

`device_pool` の `(lease, shutdown)` の対は、すでに適切な継ぎ目です。watch のループはプールを一度
作り、周ごとに `run_all` を呼び、watch が終わるときに `shutdown` を呼びます。lease の内側は何も
変わらないので、lease ごとの後片付け、ネットワークの観測、証跡、デバイス制御は単発の実行と
まったく同じに振る舞います。作業は、プールの構築を `run` の本体から取り出し、単発の経路と watch の
経路の両方が呼べる形にすることです。振る舞いを変えない改修なので、独立した作業単位として先に
入れる価値があります。watch のループが、確かめられた継ぎ目の上に乗ります。

### 何を監視し、どう検知するか

監視する集合は、コマンドラインで名指しされたシナリオファイルと、それらが参照するすべてのファイル
— `use:` の component と `dataFile` の CSV — です。この集合はすでに正確に計算されています。
`load_expanded_scenarios` は各参照を `contained_ref`（`bajutsu/common/scenario/load_expanded.py:21`）
で解決するので、監視側はグロブで当て推量をせず、解決が実際に触ったパスを記録します。ディレクトリを
指した起動でスイートのディレクトリにファイルが追加された場合は、次の周の読み込みで集合に加わります。

変更の検知は、その集合に対する更新時刻とサイズのポーリングで、標準ライブラリだけで行います。今日の
ツリーにファイルを監視するものはありませんし、ネイティブの監視機構は、どのみち正しさのために
ポーリングが必要な機能のために、決定的な経路へ新しい依存を持ち込むことになります。ファイルを
その場で書き換える保存は、粗い時計のもとでは更新時刻が変わらないことがあるため、サイズも比べます。
ポーリングの間隔はフラグで、既定値は小さく、複数ファイルの保存が何周にもならないようにまとめます。

### 不正なファイルでセッションは終わらない

読み込みエラー — 不正な YAML、未知の component、スイートのルートの外を指す参照 — は `run` が印字する
のと同じメッセージで報告し、watch は待ち続けます。ループの価値の大半はここにあります。保つ価値の
ある状態とは、まさに今日の構文エラーが壊してしまう状態だからです。デバイスやランナーの障害は別で、
実行の経路がすでに扱っているとおりに扱います
（[BE-0354](../BE-0354-xcuitest-wedge-fastfail-device-replacement/BE-0354-xcuitest-wedge-fastfail-device-replacement-ja.md)）。
応答しなくなったセッションは検知され、デバイスはプールの中で置き換えられ、watch は終わりません。
寿命の長いプールは単発の実行よりそれらの経路に出会いやすく、それは watch 専用の復旧を足すのではなく
既存の復旧を使う理由になります。

### 終了ステータスは判定ではない

`run --watch` は中断されるまで動き続けます。終了ステータスが報告するのは watch がきれいに終わったか
どうかで、合否を符号化することは決してありません。判定は今までどおり、周ごとの判定行と各周の
マニフェストです。CI が呼ぶのは `bajutsu run` であって `--watch` ではありません。単発の実行を
保管するためだけに意味を持つフラグ（`--zip-run`、`--upload-exec`）との併用は拒否するので、この形が
ゲートと取り違えられることはありません。第一原則には触れません。ここにモデルは影も形もなく、判定に
至る道筋も何も変わりません。

### Author エディタとの関係

[BE-0262](../BE-0262-serve-author-live-step-picker/BE-0262-serve-author-live-step-picker-ja.md) は
すでに `serve` の Author エディタにブラウザからの target 単位の実行を与えていて、下地の必要は同じ
です。人の反復をまたいでデバイスを開いたままにすることです。両者は、それぞれが継ぎ目を生やすのでは
なく、取り出したプールの継ぎ目を共有すべきです。この項目は継ぎ目と端末側のループを作ります。
エディタをその上に載せ替えるのは後続の作業です。

### 最初の版に意図的に入れないもの

変更が影響するシナリオだけを再実行することです。`impact`
（[BE-0321](../BE-0321-test-impact-analysis/BE-0321-test-impact-analysis-ja.md)）はまさに集合を
絞る解析で、両者をつなぐのは魅力的です。しかし、著者が実行されると思っていたシナリオを黙って
飛ばす watch は、全部を実行する watch より悪いものです。そして最初の版には、どの絞り方なら著者が
信頼するかについての証拠がありません。最初の版は、コマンドラインが名指ししたものを再実行します。

### 作業分解（MECE）

1. **プールの継ぎ目を取り出す** — プールの構築と `shutdown` を `run` の本体の外へ出し、両方の経路
   から呼べるようにします。振る舞いは変えません。
2. **監視する集合** — 参照の解決が触ったパスから記録します。ディレクトリを指した起動で追加された
   ファイルも含みます。
3. **ポーリングとまとめ** — 標準ライブラリによる変更検知、間隔のフラグ、複数ファイルの保存を
   1 周にまとめる処理。
4. **反復のループ** — 周ごとの判定行、実行ディレクトリ、実行 ID。読み込みエラーはセッションを
   終わらせずに報告します。
5. **フラグの門番と終了ステータス** — 単発実行の保管用フラグとの併用の拒否と、判定ではなく終了を
   報告するステータス。
6. **ドキュメント** — CLI リファレンスの項目、シナリオのガイドへの執筆ループの注記、および両方の
   日本語版。

## 検討した代替案

- **失敗したステップから、画面に残ったアプリの状態を使い回して再実行する。** 却下します。シナリオの
  結果が前の周に依存することになり、それは第二原則が守ろうとしている決定性そのものです。しかも
  CI のどの実行も再現できないマニフェストができるので、著者がデバッグに使う証跡と、ゲートが生む
  証跡が別物になります。
- **外部のファイル監視ツールに `bajutsu run` を呼び直させる。** 今日すぐ使えますし、コードは 1 行も
  要りません。だからこそ挙げておく価値があります。それでも却下します。プロセスごと呼び直すので、
  節約できるのは著者のキー入力だけで、コールド起動は 1 秒も節約しません。それこそこの項目が
  取り除こうとしている費用です。構文エラーをまたいでセッションを保つこともできません。再起動する
  対象が、まさに失敗したそのプロセスだからです。
- **ネイティブのファイル監視の依存を追加する。** 却下します。その場書き換えの保存を正しく扱うには
  どのみちポーリングが必要なループのために、基本インストールへコンパイル済みの依存を持ち込むことに
  なります。数十ファイルのスイートを人間の編集の速さで追うには、標準ライブラリで足ります。
- **`serve` の中にだけ作る。** 却下します。執筆の利便を、Web サーバーを動かすことに縛りつけることに
  なります。シナリオが最もよく編集されるのは端末のループです。継ぎ目を共有すれば、端末側の経路を
  ブラウザに依存させることなく、エディタにも同じ恩恵が届きます。

## 進捗

> 開発の進行に合わせて常に最新の状態に保ってください。チェックリストは *詳細設計* の MECE な
> 作業分解（作業の単位ごとに 1 つ）に対応し、ログには変更内容と時期（古い順）を PR へのリンクと
> ともに記録します。

- [ ] プールの継ぎ目の取り出し（振る舞いは不変）。
- [ ] 参照の解決から記録する、監視する集合。
- [ ] ポーリング、間隔のフラグ、変更のまとめ。
- [ ] 反復のループ。セッションを終わらせない読み込みエラーを含みます。
- [ ] フラグの門番と終了ステータス。
- [ ] 両言語のドキュメント。

構築の途中で決めるべき論点です。

- 実行中の周を中断できるようにすべきかどうか。実行の途中で届いた保存は、もう 1 周を待ち行列に
  入れるか、いま走っている周を取り消すかのどちらかです。待ち行列のほうが単純で、途中の周の証跡を
  捨てずに済みます。取り消しは、修正に手を伸ばした著者が実際に望むものです。
- watch が自分の実行ディレクトリを片づけるべきかどうか。周ごとに 1 つ溜まっていくもので、この
  ツールが生む証跡の中で最も使い捨てに近いものです。
- `--watch` が config ファイルも監視すべきかどうか。config の変更はプールを作った前提であるターゲット
  自体を変えるので、正直な応答はプールを作り直すことです。それはこの項目が扱っているコールド起動を
  払うことを意味します。やる価値はありますし、やったときには声に出して言う価値があります。
- web バックエンドにプールの取り出し以上のものが必要かどうか。あちらのレーンはデバイスではなく
  ブラウザのコンテキストだからです。
