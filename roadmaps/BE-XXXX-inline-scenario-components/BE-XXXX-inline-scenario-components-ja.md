## はじめに

シナリオファイルの内部に、インラインの `components` ブロックを宣言できるようにします。名前から
BE-0030 の**コンポーネント**（引数を取る再利用可能なステップ列）への対応表で、そのファイルの中だけ
で有効です。同じファイル内の `use: { component: <name> }` ステップは、その名前を直接解決します。
1つのファイルの中でしか使わないステップのまとまりに、別のコンポーネントファイルは不要になります。
BE-0030 が定めたファイル参照形式の `use: { component: <path> }` は変更なく動作し続けます。スイート
をまたぐ再利用は、引き続きそちらが担います。

## 動機

BE-0030 は**コンポーネント**を定義しました。引数を取る再利用可能なステップ列で、`use` ステップが
run の前にそれを呼び出し元のステップ列へ展開します。コンポーネントは常に専用のファイルに置く設計
です。`use: { component: <path> }` ステップがそのパスを解決します。そのため、わずか3ステップ程度の
短いまとまりを取り出すだけでも、新しいファイルとその名前、配線済みの相対パスが必要です。この固定
費用は、取り出した先が1つのシナリオファイルからしか呼ばれない場合でも、スイート内のすべての
ファイルから呼ばれる場合でも、同じだけかかります。

再利用が1つのファイルの中だけで完結するとき、この固定費用は割に合いません。関連する複数のシナリオ
を1つのファイルにまとめて定義することはよくあります。検索ボックスに異なるクエリを試す、フォームに
異なる入力の組み合わせを送信する、といった場合です。こうしたファイルは、同じ短いステップのまとまり
をそれらのシナリオ間だけで繰り返し、他のどこからも呼びません。そのまとまりを別ファイルに切り出すと、
ファイルが1つ増えます。読者はその新しいファイルを開いて、`use` ステップの中身を確認しなければ
なりません。呼び出し元が1つのファイルしかないコンポーネントのためだけに、です。この負担を避けたい
作者は、各シナリオへステップを手で複製します。BE-0030 がファイルをまたぐ場合について解消しようと
した重複と、同じものです。

インラインでファイルに閉じた `components` ブロックは、この局所的な場合について負担を取り除きます。
作者は、呼び出し元のシナリオと同じファイルの中にコンポーネントを定義できます。そのファイルだけで
使う名前のために、スイートのディレクトリ一覧へ項目を1つ増やす必要はありません。この変更の後では、
`components` の下でコンポーネントを定義し、同じファイル内の2つのシナリオから `use: { component:
<name> }` で呼び出すシナリオファイルがあるとします。そのファイルは、ロード時に、手で複製した場合
と同じステップ列へ展開されます。これは `bajutsu trace --explain` で展開後のステップを読めば確かめ
られ、再利用のために2つ目のファイルが作られることもありません。

## 詳細設計

BE-0030 のファイル型コンポーネントに、ファイルに閉じた兄弟を追加します。解決には同じ `use` ステップ
と、同じ `expand_components` マクロ（`bajutsu/common/scenario/expand.py`）を使います。ランナーは
これまでどおり展開済みのプレーンなステップだけを見るため、決定性は変わりません。

- **`ScenarioFile` への新しい `components` フィールド。** `ScenarioFile`
  （`bajutsu/common/scenario/models/scenario/scenario_file.py`）に、デフォルト値が空の
  `components: dict[str, Component]` を追加します。各エントリは、BE-0030 が独立したコンポーネント
  ファイルに対してすでに検証している `Component` モデル（`params` と `steps`）と同じです。1つの
  スキーマで両方の形式を扱えます。
- **名前はまずファイル内で解決し、パスはファイルとして解決し、両者は衝突しません。** `use: {
  component: <ref> }` のフィールドは1つのままです。`ref` 自身の見た目が解決方法を決めます。
  `/` を含むか `.yaml` か `.yml` で終わる `ref` は、BE-0030 がすでに解決しているとおりにファイルと
  して解決します。どちらの印もない裸の名前は、そのファイル自身の `components` マップの中でその
  キーを探します。両者は取り違えようがありません。シナリオファイル内の名前と、スイート内のファイル
  型コンポーネントは、新しいフィールドや命名規約を増やさずに同じ `use` ステップを共有できます。
- **参照の解決は `load_expanded.py` の `resolve` クロージャの中に閉じます。** `expand_components`
  の引数 `resolve: Callable[[str], Component]` は変更しません。`load_expanded_scenarios`
  （`bajutsu/common/scenario/load_expanded.py`）がそれをラップし、パス形式の `ref` について
  `contained_ref` と `load_component` へフォールバックする前に、ロード済みファイル自身の
  `components` マップを先に調べます。`expand_components` の再帰、循環検出、param の不足・未知の
  検出、ネスト深さの上限は、`resolve` が何を返しても同じように働きます。ファイル内のコンポーネント
  がファイル型のコンポーネントを `use` することも、その逆も、新しいコードパスなしに動作します。
- **新しいパス封じ込めの対象は増えません。** ファイル内のコンポーネントは、ローダがすでに読んだ
  シナリオファイルの一部として1回だけ解析されます。名前の解決が2つ目のファイルを開くことはない
  ため、BE-0174 の封じ込めチェックが新たに守るべき対象はここにはありません。
- **合意どおりファイルに閉じます。** `components` はファイルごとに読み込まれます。スイート
  ディレクトリ内の他のファイルへ合成されることはありません（`load_scenarios_dir` は各ファイルを
  独立にロードします）。あるファイルで宣言した名前は他のファイルから見えないままで、ファイルを
  またぐ再利用は引き続き BE-0030 のファイル参照が担います。

```yaml
# 1つのシナリオファイル。別のコンポーネントファイルは不要
components:
  search:
    params: [query]
    steps:
      - type: { text: "${params.query}", into: { id: home.search }, submit: true }

scenarios:
  - name: 犬で検索すると1件返る
    steps:
      - use: { component: search, with: { query: dog } }
    expect:
      - label: { sel: { id: home.status }, equals: "1 result" }
  - name: 猫で検索すると2件返る
    steps:
      - use: { component: search, with: { query: cat } }
    expect:
      - label: { sel: { id: home.status }, equals: "2 results" }
```

## 検討した代替案

**スイート全体を暗黙に検索するレジストリ（裸の名前をすべてのファイルから探す）。** 不採用です。
今回の再利用が1つのファイルの中だけで完結するという点は、ユーザー自身が確認しています。スイート
全体から裸の名前を探す設計は、この境界を BE-0030 のスイートをまたぐ役割へ押し戻してしまいます。
BE-0174 が閉じたパス封じ込めの論点も呼び戻します。実ファイルという答えがすでにある場合について、
その論点を蒸し返す理由はありません。

**ファイル内再利用のための YAML アンカーとマージキー。** 不採用です。理由は、BE-0030 がスイートを
またぐ再利用について同じ選択肢を退けた理由と同じです。アンカーは、`with` が `params` へ値を渡す
ような、名前付きで検証済みの引数を取れません。呼び出し元は、展開後のテキストを手で書き換えない
限り、呼び出しごとに再利用ブロックの中身を変えられません。

**`use` に区別用の構文を足す案（例えば `component: "local:<name>"`）。** 不採用です。代わりに
`ref` 自身の見た目、パス的な `ref` か裸の名前かで判定します。このリポジトリの既存シナリオが持つ
ファイル参照は、すでにすべて `.yaml` か `.yml` で終わっています。見た目による判定なら、`use` に
新しい構文を足す必要も、この変更より前に書かれたシナリオを書き換える必要もありません。
